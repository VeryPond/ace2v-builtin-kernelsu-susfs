# LK 层 AVB 门禁分析与修补

承接 `LK_EXPLOIT.md`。第 1 层（MTK 证书）绕过成立后，`lk` 本体可自由
修改，于是可以处理第 2 层（AVB 门禁）。

---

## 1. LK 侧关键地址

偏移为 `lk` 子镜像内偏移（该子镜像在分区文件中从 `0x200` 起）。

| 地址 | 内容 |
|---|---|
| `0x30fbc → 0x8229c` | 计算 `img_auth_required`：按分区名查表（表在 `.data 0xf9108`，条目 0x30 字节，候选字段 `+0x20/+0x24/+0x28/+0x2c`，由校验模式二选一） |
| `0x51318-0x51338` | `[AVB] img_auth_required = %d` 打印；`0x51330: cbnz w21, #0x5135c` 决定是否需要认证 |
| `0x51338` | 不需要认证分支：`mov w28,#1; mov w0,#2`（状态=2 → Orange State 警告） |
| `0x5135c` | 需要认证分支：`mov w28,#0; mov w0,#3` |
| `0x514c4` | `bl #0x92060`：AVB 实际校验调用 |
| `0x515c8 / 0x515e4 / 0x515f8 / 0x515fc` | `w23 = (img_auth_required==0)`；`w23==1` 时跳过 `0x515fc` 的 AVB 失败判定 |
| `0x519cc` | 读状态全局 `0xce00d18`；=2 显示 Orange State 并等待 5 秒；=1/3 直接尾调 `0x5307c` |
| `0x50f84` | dm-verity 状态设置（由状态值驱动） |
| `0x52fd4` 等 | `double_check_lock_state`：比对 seccfg 与 RPMB 记录的锁状态（**本次未触碰**） |

---

## 2. 修补策略与两次尝试

目标：让 AVB 校验失败不再致命，同时保持设备既有的状态语义。

| 版本 | 改动 | 结果 |
|---|---|---|
| v1 | `0x51530` NOP **＋** `0x51538` `mov w0,#2`→`#3` | **卡第一屏** |
| v2 | **仅** `0x51530` NOP | **Orange State → 正常进系统** |

### 2.1 v1 失败原因

v1 净效果是「跳过认证（`w28=1`）」＋「对外声称已验证（状态 3）」。
该组合在代码中**不存在对应路径**，故挂起。

### 2.2 v2 成功的机制

`0x51330` 的 `cbnz w21, #0x5135c` 改为 `nop`（4 字节 `d5 03 20 1f`）
→ `img_auth_required` 被忽略 → AVB 失败不再致命。

保持状态 2（与"不需要认证"语义一致），符合设备对未解锁状态的既有处理。

---

## 3. 效果与代价

- 引导链允许被修改的 `boot` 引导
- 锁状态（seccfg / RPMB）**全程未改动**
- 代价：显示 Orange State 警告（约 5 秒），这是状态值 2 的正常表现

## 4. 未处理项

1. **Orange State 警告**：可改 `0x519cc` 中对状态 2 的判断
   （如 `0x519ec` 的 `cmp w8,#2`）使其不走警告分支，
   但 `androidboot.verifiedbootstate` 可能仍上报 orange。
2. **dm-verity（第 3 层）**：由 `0x50f84` 与状态值驱动；
   改过的 `system` 是否被内核接受尚未验证。

## 5. 与本仓库主线的关系

本仓库最终采用的方案是**保留 LK 的既有状态**，改为在**内核层**
解决内核信息暴露问题（见 `ARCHITECTURE.md` 第 8 节）。
本节记录的是 LK 侧的分析与可行修补，供需要更深层控制时参考。
